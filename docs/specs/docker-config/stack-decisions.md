# Stack Decisions: `devstuff configure docker`

**Date:** 2026-08-02
**Context:** The fourth configurator. SD-1 and SD-2 in `docs/specs/starship-config/`
(configurators are Python modules in a registry, keyed in Python rather than declared in
`tools.yaml`) apply unchanged and are not restated. Everything below is specific to Docker.

---

## SD-1 — The wizard's checks run *alongside* the real validator, not instead of it

**Decision: `verify()` runs `dockerd --validate` and a set of checks the validator does not
perform, and presents both as one report.**

Every other configurator in this repo defers to the tool's own checker, on the principle that
measuring beats reimplementing. That principle still holds here — `--validate` catches key
typos and malformed CIDRs, which a hand-written check set would have to duplicate — but it is
not sufficient. Five configurations were measured passing `--validate` and then breaking every
`docker run` (see the table in `specifications.md`).

- **Rejected — trust `--validate` alone.** It is the natural reading of "measure, don't
  reimplement", and it would ship a wizard that cheerfully writes a config making the machine
  unable to start a container.
- **Rejected — replace `--validate` with the wizard's own checks.** Then a key typo, which the
  validator catches perfectly, would reach the user.
- **Rejected — try starting a container to prove the config.** The only thing that would test
  FR-18 end to end, and it needs a running daemon, a pullable image, and permission. Far past
  what a config wizard should assume (Open Question 5).

**Consequence:** `validate.py` is bigger than its equivalents in the other configurators, and
each extra check carries a comment recording the measurement that justifies it. The module
docstring holds the table.

## SD-2 — An existing `daemon.json` *is* round-tripped, unlike a pre-commit config

**Decision: `detect.from_existing()` reads the file back into wizard state, and every key the
model does not know about is preserved in `DockerConfig.extra` and written back untouched.**

The pre-commit configurator refuses to do this (its SD-6), and the reasoning there was sound: a
`.pre-commit-config.yaml` carries comments, ordering, `repo: local` hooks and per-hook
overrides, so a partial round-trip silently discards things the project depends on.

None of that applies to `daemon.json`. It is a flat JSON object. There are no comments to lose,
key order carries no meaning, and every value is a JSON scalar or container. A faithful
round-trip is not just possible, it is checkable — and it is checked, over a realistic
hand-written config with three unmodelled keys.

- **Rejected — refuse to read it, as pre-commit does.** It would mean a user with a tuned
  `daemon.json` cannot use the wizard at all without losing their tuning, on a file where
  preserving it is straightforward.
- **Rejected — read only the keys the model knows.** This is the silent-loss failure the
  pre-commit spec rightly rejects. `extra` is what makes the difference between "we understood
  the parts we understood" and a faithful round-trip.

**Consequence:** the `current` preset exists, `suggest()` opens on the existing config rather
than a preset, and `test_a_hand_written_config_round_trips_without_loss` asserts the emitted
file equals the input exactly.

## SD-3 — Only non-default values are written

**Decision: a setting equal to the daemon's own default is omitted from the file entirely.**

The alternative — write every modelled key — produces a config that documents itself, which is
genuinely tempting for a generated file.

But `daemon.json` is read by a daemon that gets upgraded. A config restating today's defaults
*freezes* them: when a future Docker changes a default, every machine carrying such a file
keeps the old behaviour, and nothing indicates why. The user never chose that value; the wizard
did, on their behalf, permanently.

- **Rejected — write everything, for documentation.** Turns "I accepted the defaults" into "I
  pinned the defaults as of the day I ran a wizard".
- **Rejected — write everything with the defaults commented out.** JSON has no comments. This
  is also why the file cannot carry a "generated by devstuff" marker (SD-4).

**Consequence:** `Setting.default` must equal the corresponding `DockerConfig` field default, or
the emitter writes keys nobody asked for. That is a test rather than a convention.

## SD-4 — Overwriting shows a diff instead of checking for a marker

**Decision: the overwrite prompt renders a unified diff of the change and asks.**

The pre-commit and commitizen configurators detect their own previous output by a generated
header comment, and replace it without ceremony. JSON has no comment syntax, so there is
nowhere to put a marker and no way to tell the wizard's output from a hand-written file.

Having to solve it differently turned out better. A marker answers "did I write this?", which
is a proxy. A diff answers "what am I about to change?", which is the actual question — and it
is equally useful whether the file was hand-written or generated.

- **Rejected — a sidecar marker file.** State about a config, stored next to it, that any edit
  invalidates and nothing else maintains.
- **Rejected — an unrecognised key as a marker.** `dockerd --validate` rejects unknown keys, so
  a marker would make the config invalid. Measured, not assumed.
- **Rejected — always overwrite.** This file can be the difference between a host that boots
  containers and one that does not.

**Consequence:** `render.diff()`, and a save that reports "already contains exactly this" and
writes nothing rather than churning a timestamp.

## SD-5 — Writing and applying are two separate confirmations

**Decision: saving the file and restarting the daemon are asked about separately, and the
restart question states how many containers it will stop.**

A written `daemon.json` changes nothing. The daemon reads it at start-up, so the config is
inert until `systemctl restart docker` — which stops every running container unless
`live-restore` was already on.

That last word is the subtlety and the reason this is not a single "save and apply" step.
Turning on `live-restore` in the config being saved does *not* protect the restart that applies
it; it protects the next one. So the warning reads the daemon's current state, not the new
config's.

- **Rejected — restart automatically after saving.** Silently killing running containers is the
  worst thing this wizard could do, and "I changed the log rotation" gives no reason to expect it.
- **Rejected — never restart, just print the command.** Leaves every user one forgotten step
  from believing they fixed a problem they have not fixed.
- **Rejected — `systemctl reload docker`.** Reload re-reads only a subset of `daemon.json`, and
  which subset is version-dependent. A wizard that reloads and reports success, having applied
  half the file, is worse than one that states the cost of a restart.

**Consequence:** `_offer_restart` reads `found.live_restore`, and after a successful restart the
daemon is asked what it now believes (FR-21) rather than the save being assumed to have worked.

## SD-6 — Root-owned writes go through `sudo install`, staged via a temp file

**Decision: the config is written to a temp file, then moved into place with
`sudo install -m 0644 -o root -g root`, with the command shown first.**

This is the only configurator whose target is outside the user's home, which introduces two
problems the others do not have: the write needs privilege, and a write interrupted partway
leaves a daemon reading a truncated config.

- **Rejected — `sudo tee`, or a shell redirect under sudo.** A redirect truncates the
  destination before writing, so a failure or an interrupt destroys the existing config. Staging
  and moving makes the replacement atomic.
- **Rejected — re-exec the whole wizard under sudo.** Runs an interactive questionary session as
  root for the sake of one write, and puts the user's own config and cache under root ownership.
- **Rejected — write it and tell the user to move it.** A two-step manual process at the exact
  point where getting it wrong means the daemon does not start.

**Consequence:** `validate.write()` and `validate.backup()` both take a `sudo` flag and mirror
each other; a root-owned file needs privilege to copy as well as to replace. `Docker.writable()`
decides which path is taken, so a rootless daemon — whose config is in the user's home — never
invokes sudo at all.
