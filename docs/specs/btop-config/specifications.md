# Specification: `devstuff configure btop` and the `btop` catalog tool

**Date:** 2026-10-19
**Status:** Implemented (v1)
**Authors:** Sawyer + Devin

---

## 1. Problem Statement & Goals

btop's validation is asymmetric in *three* classes, and two of them are silent.
Measured against 1.3.0 (Ubuntu 24.04 apt), 1.4.6 (Ubuntu 26.04 apt, GPU build) and
1.4.7 (upstream static musl):

| what you write                          | btop's reaction                                  |
|-----------------------------------------|--------------------------------------------------|
| `update_ms = "abc"`, `vim_keys = yes`, `graph_symbol = "bad"` | rejected, reset to default, WARNING in btop.log |
| `shown_boxes = "cpu foo"`               | rejected, reset, **nothing logged**              |
| `proc_sorting = "bogus"`, `temp_scale = "bogus"`, an unknown `color_theme` | **kept verbatim**, silently falls back, nothing logged |

So a hand-edited `btop.conf` can carry values that are dead (reset on every load)
and values that are alive-but-wrong (kept and silently ignored), and btop will
not distinguish either. The live check — run btop and diff what it saved back —
only sees the first two classes; the third needs an offline check, which is why
the wizard has both halves and why neither is redundant.

The second problem is what btop does to the file itself: it rewrites the *whole*
config — every key and its own comments — whenever the first line is not this
version's `#?` header, when a value was rejected on load, or when a setting was
changed in-app (`save_config_on_exit = true`; 1.3.0 always saves). Otherwise it
leaves the file byte-identical, comments and unknown keys included. A wizard that
rewrote the file on every save would destroy comments it didn't write; a
"generated by devstuff" marker would be a lie the first time btop saves.

Third: the key set varies by version *and* build flags — `disable_mouse` arrives
in 1.4.7, `shown_gpus` exists only on GPU builds, `save_config_on_exit` doesn't
exist before 1.4. A fixed table is wrong on every other binary.

**Goals**

- Splice into the existing file — replace values in place, append only needed
  keys, never delete or reorder anything.
- Check offline before every save; check live against the real binary (it is the
  only authority on what it keeps), and say what each check cannot prove.
- Ask only about keys this build knows, and never write one it does not.
- Offer the `cap_perfmon` capability grant — documented upstream as required for
  CPU package watts and Intel GPU stats — with the privilege-hole refusals and
  the apt-upgrade caveat stated.
- Nothing written until confirmed; an existing file is always diffed first.

**Non-goals**

- The `presets` string and per-box layout editing (`cpu:1:default,…` — a
  different, much more positional format; btop's own UI is where that lives).
- Per-box graph symbols (`graph_symbol_cpu` etc.) — one global `graph_symbol`.
- GPU/disk/network filters (`disks_filter`, `net_iface`, `shown_gpus`
  membership), `cpu_graph_*` selections — machine-specific pickers.
- Custom theme authoring.
- `setuid` — `cap_perfmon` is upstream's preferred mechanism.
- `profile` support — pins/install only; out of scope here.

## 2. Functional Requirements

### Catalog

- **FR-1** `btop` is a built-in `apt` tool (`apt_packages: btop`) with
  `check_cmd: btop`, in the `test-installs.yml` matrix and the README table.

### Model

- **FR-2** Settings are data in `configure/btop/model.py`: `SETTINGS` is ordered
  (declaration order is prompt order), each `Setting` carries `kind`
  (`bool|int|str|enum|theme|boxes`), `default`, `label`, `description`, optional
  `choices`/`minimum`/`maximum`, and `group`. Enum `choices` are the values
  btop's own `--default-config` comments list.
- **FR-3** `BtopConfig` carries one field per setting and `field default ==
  Setting.default` — a test pins the pairing.
- **FR-4** Five presets: `defaults`, `low-overhead`, `basic-glyphs`,
  `processes`, `current` (offered only when a config exists). **No preset sets
  `save_config_on_exit`** — it changes how btop treats the file; only the user's
  explicit answer may (a test).

### The file

- **FR-5** `render.to_text` splices: base = existing file text if the target
  exists, else a minimal new file whose first line is *this binary's* `#?`
  header verbatim (never constructed — `v.1.4.6` vs `v. 1.3.0` differ) plus a
  comment explaining the rewrite-on-save behaviour.
- **FR-6** For every modelled key the binary knows: an existing line's value is
  replaced in place iff the parsed value differs (keeping spacing, comments and
  every other byte); an absent key is appended only when it differs from the
  effective default (`found.defaults` parsed, falling back to `Setting.default`).
  Lines are never deleted; a key the binary does not know is never written.
- **FR-7** `render.parse` keeps every original line and reads values the way
  btop does: `"s"` ends at the second quote, `true`/`false` are case-insensitive,
  a trailing ` # comment` is stripped, a bare word is a string.
- **FR-8** `render.matches` parses the result back and compares — the splice
  verifies itself like commitizen's pyproject splice.
- **FR-9** `--output <path>` writes elsewhere; the try-it hint names `btop -c`
  only when the detected version supports it (1.4+; 1.3.0 has no `-c`).

### Detection

- **FR-10** The config dir is `$XDG_CONFIG_HOME/btop` when set and non-empty,
  else `~/.config/btop`; the file is `btop.conf`.
- **FR-11** The key set, header and raw defaults come from
  `btop --default-config` when it works, else a first-run probe: btop under a
  pty in a throwaway HOME writes the same file. `keys` is `None` when neither
  could be read — the difference between "not installed" and "no keys".
- **FR-12** Themes = `Default`, `TTY`, plus `*.theme` stems in
  `<binary>/../share/btop/themes`, `/usr/local/share/btop/themes`,
  `/usr/share/btop/themes` and `<config_dir>/themes`, deduplicated. A full path
  is never a theme value.
- **FR-13** `detect.running` lists pids of `btop` processes owned by this user —
  a running btop reads the config only at start and can overwrite the file on
  exit.
- **FR-14** An existing config is read back into wizard state (`preset
  "current"`). A value btop itself would reject — wrong type for kind, an int
  out of range or negative, a bad `graph_symbol`, an unknown `shown_boxes`
  token — becomes the effective default and is recorded in `invalid_existing`
  for the report. A silently-kept value (`proc_sorting = "Memory"`, an unknown
  theme, an empty `shown_boxes`) is carried as-is so `verify` can flag it.

### Verification

- **FR-15** `validate.verify` runs offline before every save: splice round-trip;
  types and ranges; enum values in their choices; the theme exists in
  `found.themes` (a list that could not be read passes with an "unverified"
  detail, never a false accusation); `shown_boxes` tokens valid (gpuN only when
  `shown_gpus` is in the key set) and non-empty; no `"` or newline inside a
  string value; every wanted non-default key known to this binary (the check
  passes with an explanatory detail when the key set is unknown).
- **FR-16** `validate.launch` writes the candidate to `<tmp>/.config/btop/
  btop.conf`, starts the real binary under a pty with a minimal environment
  (HOME, TERM, LANG, PATH only — no `-c` flag exists before 1.4, no inherited
  XDG), answers `ESC[6n`, quits with `q`, reaps, and diffs what the file says
  now. A `Rejection` is a modelled key saved back with a different value, or a
  candidate key that vanished from a *rewritten* file. btop.log lines mentioning
  the key attach as detail; a WARNING alone is never a rejection.
- **FR-17** A btop that did not start is a failed check with an escaped tail of
  its output. A passing launch is stated as not proving enum values or the
  theme — btop keeps those silently.
- **FR-18** `launch` is an explicit menu action and runs once at save time when
  btop is installed. A failed check at save asks "Save anyway?" (default No); it
  never silently blocks.

### The capability

- **FR-19** After a successful save — only when the real config was written and
  btop is installed — the wizard offers `sudo setcap cap_perfmon=+ep <binary>`,
  default No, explaining: required for CPU package watts and Intel GPU stats
  (upstream `make setcap`, preferred over setuid); applies to every user of the
  binary; an apt upgrade replaces the binary and drops it. If already set, it
  offers removal (default No). It is verified by `getcap`, not by whether watts
  appear — unknowable where power counters are hidden.
- **FR-20** The grant is refused — with the reason and the command printed —
  when `setcap` is missing, the binary is not root-owned, or it is
  group/other-writable (a capability others can replace is a privilege hole).
  Never offered under `--output`.

### Saving

- **FR-21** An existing target is always diffed and confirmed (default No) —
  there is no reliable generated-by marker because btop rewrites the file. A
  timestamped `<name>.bak.<YYYYmmdd-HHMMSS>` is kept.
- **FR-22** After saving, running btop processes are called out (restart to
  pick it up; one started with save-on-exit can overwrite the file).

## 3. Non-Functional Requirements

- **NFR-1** Zero new runtime dependencies (stdlib pty/fcntl for the live check).
- **NFR-2** Unit tests require neither btop nor the network; live tests skip
  without `btop` on PATH.
- **NFR-3** No import of the wizard at CLI start-up.
- **NFR-4** `verify()` is instant; `launch()` costs ~5 s and the UI says so.
- **NFR-5** Every failure path returns `None`, an empty value or a failed
  `Check` — nothing raises into the wizard.
- **NFR-6** Outside text — log lines, file values, paths, exception text — is
  escaped with `rich.markup.escape` before it reaches `ui.*`.

## 5. Findings That Changed the Design

- **The three validation classes** (§1). The live check is real and useful —
  and blind to the kept-silently class, so `verify` carries the enum/theme/boxes
  checks. Both halves are tested as able to fail.
- **btop rewrites or leaves alone, never merges** (§1). Hence the splice, the
  "always diff before overwrite" rule and the absence of a generated marker.
- **`--default-config` does not exist before 1.4**, and neither does `-c` — so
  detection falls back to a first-run pty probe and the live check isolates
  HOME instead of passing a config path.
- **The key set depends on build flags too** — the apt 1.4.6 GPU build has
  `shown_gpus`/`graph_symbol_gpu`/`custom_gpu_name0..5` that upstream's static
  1.4.7 lacks, and 1.4.7 has `disable_mouse`/`proc_follow_detailed` that 1.4.6
  lacks. Only the binary's own dump is authoritative.
- **`save_config_on_exit` can never be preset-decided** — with it on, a running
  btop you touch rewrites this file on exit (measured); with it off, the file is
  authoritative and in-app changes are session-only. The wizard explains both.
