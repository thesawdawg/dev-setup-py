# Stack Decisions: `devstuff configure btop`

**Date:** 2026-10-19
**Context:** The tenth configurator. SD-1 and SD-2 in
`docs/specs/starship-config/` apply unchanged. This is the first configurator
whose tool *rewrites its own config file*, and most of the decisions follow
from that and from the three-class validation split.

---

## SD-1 — Install type: `apt`, not the upstream static binary

**Decision: the catalog entry is `type: apt`, `apt_packages: btop`.**

User decision, 2026-10-19. The upstream release binary is a static musl build
with **no GPU support** (measured: `GPU_SUPPORT=false`, no `shown_gpus` key);
the distro package on a current Ubuntu is 1.4.6 *with* GPU support, and apt is
how a tool like this is normally maintained. The trade: apt's version lags
upstream (24.04 ships 1.3.0, which lacks `save_config_on_exit`,
`disable_mouse` and `--default-config`) — absorbed by the version-aware key
set rather than by pinning a version.

- **Rejected — `type: bash` fetching the upstream tarball.** Loses GPU support
  for most users and replaces apt's upgrade/remove path with a private one.
- **Rejected — `type: bash` building from source.** A C++ toolchain + CMake
  for a monitor is disproportionate.

**Consequence:** every per-version difference (keys, `--default-config`, `-c`,
`save_config_on_exit`) is probed at run time — the wizard cannot assume a
version.

## SD-2 — Splice, not rewrite

**Decision: `render.to_text` edits the existing file in place — values replaced
inside their own lines, keys appended only when absent *and* non-default —
and never deletes, reorders or regenerates the file.**

btop's own contract is all-or-nothing: it rewrites the whole file (its
comments, its key order) or leaves it byte-identical, and the rewrite triggers
are a wrong-version header, a rejected value, or an in-app change. A wizard
that rewrote the file on every save would (a) delete user comments and
unmodelled keys, and (b) look *exactly like* a btop rewrite — the two authors
would be indistinguishable. Splicing keeps the wizard's footprint smaller than
btop's own and preserves everything the wizard doesn't model.

- **Rejected — emit a complete `key = value` file like the other
  configurators.** Loses comments and unmodelled keys every save; also
  misrepresents which file btop will show back.
- **Rejected — write only a sparse overrides file.** There is no includes
  mechanism; btop.conf is the only file.

**Consequence:** the emitter needs a real parser (`render.parse` keeps every
line and each value's slice), and `matches()` round-trips it for `verify`.

## SD-3 — No generated-by marker; overwrite is always a diff + confirm

**Decision: the wizard does not write a "generated by devstuff" marker, and
saving over an existing file always shows the diff and asks (default No).**

A marker cannot survive: the first in-app change or btop upgrade rewrites the
file and drops it, so "marked" and "user's" stop being distinguishable the
moment btop runs — the marker would certify authorship it cannot prove. The
diff answers the real question (what will change) better than provenance does.
This deviates from the bat/pre-commit pattern deliberately, and the new file
carries a comment about the rewrite behaviour instead.

- **Rejected — a marker comment, like bat's.** Silently false after any btop
  save; the `found.generated` shortcut it enables would then skip the diff on
  files the user did edit by hand inside btop.

## SD-4 — HOME isolation for live checks, never `-c`

**Decision: `launch()` and the 1.3.0 defaults probe run btop under a pty with a
throwaway HOME and a minimal environment — `HOME`, `TERM`, `LANG`, `PATH` and
nothing inherited (no `XDG_*`).**

`-c/--config` would be the obvious way to point btop at a candidate file, but
it does not exist before 1.4 — on 1.3.0 it exits 1. HOME isolation works on
every version: config lands at `$HOME/.config/btop/btop.conf`, the log at
`$HOME/.local/state/btop.log`. The minimal env also keeps a stray
`XDG_CONFIG_HOME` from redirecting the sandboxed config into the user's real
one.

- **Rejected — `btop -c <file>`.** Version-gated; two live paths where one
  suffices.
- **Rejected — inherit the user's environment.** Leaks `XDG_CONFIG_HOME` into
  the sandbox and could point the run at the real config.

## SD-5 — The live check is a value diff, not a log read

**Decision: `rejections()` compares the candidate's values to what the saved
file says; btop.log lines only annotate rejections the diff already found.**

Measured: the GPU build logs `WARNING: Intel GPU: Failed to initialize PMU` on
every start on some hosts — a log-driven verdict would call every good config
bad and every silent rejection invisible. The value diff is exact: a rejected
value comes back as the default (btop rewrites the file when it rejects), and
an unknown key vanishes from a rewritten file. The asymmetry is also pinned by
a live test: `proc_sorting = "bogus"` produces *no* rejection — if a future
btop starts validating it, the suite notices.

- **Rejected — grep btop.log for WARNING.** False positives (the GPU noise)
  and false negatives (the silently-reset `shown_boxes` class) at once.

## SD-6 — The capability is verified by `getcap` only

**Decision: `grant`/`revoke` run `sudo setcap` and re-read with `getcap`; the
wizard says it proves the capability is set, not that watts appear.**

Whether `cap_perfmon` then yields CPU package watts depends on the power
counters being visible — on a container or VM they often are not, and there is
no honest check for it from here. So the verification boundary is stated in
the UI, and the refusals (missing setcap, non-root-owned or writable binary)
are checked *before* the offer: a file capability on a binary others can
replace is a privilege escalation hole, not a fix.

- **Rejected — setuid.** Upstream documents `setcap` as preferred; setuid
  grants everything root has to read two counters.
- **Rejected — probe `/sys/class/powercap` and infer.** Container-visible
  rules vary; an honest "cannot tell" beats a wrong promise.
- **Rejected — verify via a btop run.** Watts-absent could mean hidden
  counters *or* a missing capability; the ambiguity is the thing being
  avoided.

## SD-7 — Detection asks the binary for its key set

**Decision: `found.keys`, `found.header` and `found.defaults` come from
`btop --default-config`, or — on 1.3.0, which lacks the flag — a first-run
probe that reads the file a pty'd btop writes into a throwaway HOME.**

The key set depends on version *and* build flags (SD-1): 1.4.7 has
`disable_mouse`/`proc_follow_detailed`, the apt 1.4.6 GPU build has
`shown_gpus`/`graph_symbol_gpu`/`custom_gpu_name0..5`, 1.3.0 has neither plus
no `save_config_on_exit`. The header text is taken verbatim (`v.1.4.6` vs
`v. 1.3.0` — a space) because constructing it would guess at exactly the
string the rewrite check keys on. `keys` `None` is a real state — "could not
ask" — that keeps the wizard fully functional offline by offering every
modelled setting.

- **Rejected — a per-version key table in the model.** Wrong at build-flag
  level (the static 1.4.7 vs apt 1.4.6 split) and guaranteed stale.
- **Rejected — probing each key individually.** One dump answers all of it.

## Rejected, whole

- **Editing the `presets` string or per-box layout.** `presets =
  "cpu:1:default,…"` is a positional mini-language btop's own menu manages;
  modelling it buys a fragile second implementation.
- **`profile` support for btop settings.** The profile system pins installs,
  not dotfiles.
